# Trip Mate — Code Review / Audit Report

- **Date:** 2026-09-26
- **Scope:** `backend/` (66 py files, ~8,965 LOC) and `frontend/` (41 ts/tsx files, ~7,399 LOC)
- **Baseline at audit time:** `pytest tests/ -q` → **403 passed**; `npm run lint` / `typecheck` / `check:i18n` → all clean; 56 OpenAPI operations
- **Method:** read the code, then **reproduced** the high-severity findings with throwaway probe scripts. Findings carry a
  `[verified]` tag when I reproduced them; `[read]` when they follow from reading the code but were not reproduced.

> The headline caveat, stated up front: **a green test suite is not evidence of a correct one.** Every defect below is
> untested today. Two of them (`B1`, `B2`) are only reachable under concurrency, and the third (`B3`) was reproduced
> deterministically against an endpoint that already has passing tests.

## 1. Correctness

### B1 — Duplicate review causes a permanent 500 `[verified]` — **High**

**Where:** `backend/app/api/v1/reviews.py:81-96`

```py
duplicate = (
    await db.execute(select(Review).where(...))
).scalar_one_or_none()
```

**Problem.** `.scalar_one_or_none()` **raises `MultipleResultsFound`** when two rows match. Two matching rows are
reachable because `Review.trip_post_id` is nullable and SQL treats NULLs as distinct, so `uq_review_once_per_trip`
does **not** cover `trip_post_id IS NULL`. The application-level check is the only guard, and it is a check-then-act
(a concurrent double-submit both see nothing, both insert).

**Verified.** I planted two matching `trip_post_id IS NULL` rows (exactly the state a lost race leaves behind) and
called the endpoint once:

```
>>> planted: 2 matching NULL-trip rows exist
ERROR  tripmate.http  unhandled_exception {"route": "/api/v1/reviews",
                                          "exception_type": "MultipleResultsFound"}
```

The response is **500**, not the documented 409 — and it is **permanent**: every subsequent review attempt by that
pair fails the same way. The state is unrecoverable through the API.

**Fix.**
1. Change the guard to `.scalars().first()` so a pre-existing duplicate yields 409 rather than 500 — this alone removes
   the permanent-500 failure mode.
2. Close the race: add a **partial unique index**
   `CREATE UNIQUE INDEX uq_review_pair_null_trip ON reviews (reviewer_id, reviewee_id) WHERE trip_post_id IS NULL`
   (PostgreSQL) so the database is the arbiter, then catch `IntegrityError` and map it to 409.
3. Both are needed: (1) makes the failure benign for data already written; (2) stops new duplicates.

### B2 — Duplicate DIRECT chat rooms `[read]` — **High**

**Where:** `backend/app/api/v1/chat.py:71-96`, and the same select-then-insert in `trips.py::_ensure_direct_room`

**Problem.** `ChatRoom` has only `UniqueConstraint("room_id", "profile_id")` on its *members*
(`models/chat.py:37`). Nothing prevents two `DIRECT` rooms containing the same two people. The existing-room lookup
is a select-then-insert with no atomic guard, so two concurrent `POST /chat/rooms` (or two concurrent accepts, each
calling `_ensure_direct_room`) create two rooms. Messages then split across them and `GET /chat/rooms` shows
duplicates. The current test (`test_trip_group_room.py:94`) only covers the **sequential** reuse path.

**Fix.** Give the room a canonical pair key — e.g. a `direct_key` column holding the two profile ids sorted and
joined, with a unique index — and use `INSERT ... ON CONFLICT DO NOTHING` then re-select. A unique index on a derived
key is the only thing that actually closes this; an app-level re-check merely narrows the window.

### B3 — `PATCH /trips/{id}` can overbook `[verified]` — **High**

**Where:** `backend/app/api/v1/trips.py:429-439`; schema at `app/schemas/trip.py:61-73`

**Problem.** `TripPostUpdate` exposes both `looking_for_count` (`ge=1, le=20`) and `status`, and the handler does
`for field, value in changes.items(): setattr(post, field, value)` with **no re-check against already-ACCEPTED
applications**. The accept path (`trips.py:307-320`) carefully defends `accepted <= looking_for_count` under an
unconditional row lock — but this endpoint walks around it.

**Verified.**

```
>>> PATCH looking_for_count=3->1 with 2 ACCEPTED -> 200
>>> after patch: accepted=2
```

The trip is now permanently overbooked (limit 1, 2 accepted) and **no endpoint can repair it** — `decide_application`
refuses every further accept with 409, and the only recovery is a manual DB write. `status` is likewise settable to any
enum value with no transition validation (e.g. reopening a `CLOSED` trip, or setting `CANCELLED` while travellers hold
accepted seats).

**Fix.** In the PATCH handler, when `looking_for_count` is in `changes`, re-run the same accepted-count query used by
the accept path and reject with 409 if the new limit is below it. Validate `status` transitions against a small
allowed-transition table. Both belong in a shared helper so the two paths cannot drift again — **this is the same
`guarded-on-one-path-only` pattern as B1 and B5.**

### B4 — `presign` trusts a client-supplied `prefix` `[read]` — **High**

**Where:** `backend/app/api/v1/uploads.py:46-51` → `services/storage.py:127-145`

```py
key, url = presign_put(payload.content_type, prefix=payload.prefix)   # from the request body
...
key = build_key(prefix, ALLOWED_MIME[content_type])   # f"{prefix}/{uuid}.{ext}"
```

**Problem.** `PresignRequest.prefix` (default `"uploads"`) comes straight from the client and is neither validated
against an allow-list nor namespaced to the caller. Any authenticated user can obtain a signed PUT for an arbitrary
key prefix — e.g. `profiles/<someone-else's-profile-id>/…` — and the `..` sequence is unescaped. The traversal guard
in `_put_local` (`storage.py:79`) does not help because presign is S3-only. The existing test
`test_presign_key_is_server_generated_and_cannot_escape_its_prefix` pins the **library** helper, not the **route**,
which is why this survives.

**Fix.** Ignore the client prefix entirely and derive it server-side from the caller
(`f"profiles/{profile.id}"` — the sibling endpoint at `profiles.py:139` already does exactly this). If a caller-chosen
prefix is genuinely wanted, validate it against a fixed allow-list *and* reject any value containing `/` or `..`.

### B5 — Concurrent block → 500 instead of idempotent 201 `[read]` — **Medium**

**Where:** `backend/app/services/moderation.py:74-87`

```py
existing = (await db.execute(select(Block).where(...))).scalar_one_or_none()
if existing:
    return existing, False
block = Block(...); db.add(block); await db.flush()   # <-- IntegrityError on a lost race
```

**Problem.** `uq_block_pair` **does** exist (`models/moderation.py:13`), so unlike B1 the constraint is real — but the
code never handles the violation. Two concurrent identical blocks both pass the SELECT, and the loser raises
`IntegrityError` at `flush()` → **500**, where the contract is an idempotent 201. The `created` flag
(`profiles.py:213`) is designed precisely to express "already blocked", but the race never reaches it.

**Fix.** Wrap the insert in `try/except IntegrityError`, roll back, re-select, and return `(existing, False)`. That is
the standard idempotent-upsert shape and makes the endpoint match its own docstring.

### B6 — Backend returns hardcoded Chinese to English clients `[read]` — **Medium**

**Where:** `app/ws/routes.py:220`, `app/ws/routes.py:80`, `app/services/content_filter.py:246`

```py
"detail": "為保障私隱，請避免在建立信任前交換聯絡方式或進行金錢交易。"
room_label = (room.title or "行程群組") ...
detail="內容審核服務暫時無法使用，請稍後再試。",
```

**Problem.** These strings are sent to the client as user-visible text. The frontend has a fully typed zh-HK/en
dictionary (341 keys) and renders `safety_hint.detail` verbatim (`chat/page.tsx:161`, notice at `:229`), so an
English-locale user receives Traditional Chinese. This partially defeats the i18n work, and it is invisible to
`check:i18n` because that script only scans frontend sources.

**Fix.** Send a **code** plus structured params (`{"type": "safety_hint", "code": "possible_phone"}`) and let the
client map it through the dictionary — the WS error frame already does this with `code: content_rejected`. Where a
message must be server-side (notifications), store a key and render on read. Add a backend lint that flags Han
characters in `detail=`/user-facing string literals so this cannot regress.

### B7 — Cross-replica breaker compares `monotonic()` from different processes `[read]` — **Medium**

**Where:** `app/services/kv.py:708-716`, mirrored in `core/rate_limit.py:115-129`

**Problem.** `is_open()` adopts a peer's published `cooldown_until` and compares it to the **local**
`time.monotonic()`. `time.monotonic()` has no defined epoch and is **not** comparable across processes, let alone
hosts. A replica that adopts a peer's value can therefore trip for an arbitrary duration (or effectively not at all),
depending on the two processes' monotonic offsets. The degradation is fail-safe-ish (the local window is consulted
first), but the cross-replica half of #22a does not do what its docstring claims.

**Fix.** Publish an absolute wall-clock deadline (`time.time() + cooldown`) and compare wall-clock on read, keeping
`monotonic()` strictly for the local-only window. Guard against clock skew by clamping the adopted window to a
maximum.

**✅ Resolved.** Implemented exactly as described. `_BreakerState` now publishes the field `deadline`
(`_DEADLINE_FIELD = "deadline"`; the old `cooldown_until` field name is gone), and `_adopt_shared_deadline()` converts
the published wall clock to a **duration** on read — `remaining = float(published) - time.time()` — then clamps it to
`min(remaining, _COOLDOWN_SECONDS)`. `self.cooldown_until` remains a **monotonic** value and is only ever compared
against `time.monotonic()`. A negative `remaining` (expired, or our clock ahead of the peer's) is skipped; a
non-numeric value is ignored rather than raising. Covered by five tests in `tests/test_multi_replica_hardening.py`,
including one that offsets the follower's `time.monotonic` by −6 hours to prove the adoption no longer depends on the
two processes sharing an epoch. Negative-validated 3/3: reverting to publishing `self.cooldown_until` raw reddens the
wall-clock, the monotonic-offset and the clamp tests.

### B8 — Five `DELETE` endpoints lack rate limiting `[read]` — **Low**

**Where:** `chat.py` no; specifically `notifications.py:141`, `profiles.py:162`, `profiles.py:228`,
`trips.py:445`, `users.py:20`

**Problem.** All POST/PATCH counterparts carry `@limit(WRITE_RATE)` (15 decorators across 6 modules), but these five
DELETEs have none. Impact is low — they are idempotent and cheap — but a destructive endpoint with no ceiling is an
inconsistency, and cheap deletes are exactly what a scripted abuser uses to clear their tracks or harass by
re-creating.

**Fix.** Add `@limit(WRITE_RATE)` for symmetry. Consider a `DESTRUCTIVE_RATE` tier if the intent was to allow more
frequent deletes than writes.

**✅ Resolved — and the finding understated itself.** All five DELETEs now carry `@limit(WRITE_RATE)`. Note the audit's
line numbers for two of them were stale: `notifications.py:141` already had the decorator.

Writing a route-inventory test (`tests/test_write_endpoint_limits.py`) instead of hand-checking turned up **five more
genuinely-unrated writes**: `POST /auth/refresh`, `POST /auth/logout`, `POST /auth/password`,
`PATCH /admin/reports/{report_id}` and `POST /uploads/presign`. So the real count was 10, not 5. `REFRESH_RATE =
"30/minute"` was added to `core/rate_limit.py` — a healthy client refreshes at most once per token lifetime, so a high
rate against the refresh endpoint *is* the replay signature.

One implementation trap worth recording: slowapi requires the wrapped function to accept a `request: Request`
parameter, or importing the app raises `Exception: No "request" or "websocket" argument on function`. Adding the
decorator alone therefore breaks startup, not the request.

The suite includes `test_the_limiter_is_not_satisfied_by_a_bare_decorator`, a guard against the probe itself going
vacuous — a helper that always reports "limited" would make the other two tests unfalsifiable. Negative-validated 3/3:
stripping 28 decorators reddens both inventory tests, and making the probe return `True` unconditionally reddens the
anti-vacuity guard.

### B9 — Recommendation recency mixes a local date with a UTC timestamp `[read]` — **Low**

**Where:** `app/services/matching.py:113`

```py
age_days = (today - post.created_at.date()).days   # today = date.today()
```

**Problem.** `created_at` is timezone-aware UTC (`db/base.py:11-12`); `date.today()` is server-local. On a non-UTC
host the `<= 3` / `<= 14` freshness buckets are off by one near midnight, so scores (and therefore result ordering)
differ by deployment timezone. Non-deterministic between environments.

**Fix.** `datetime.now(timezone.utc).date()`.

**✅ Resolved.** Fixed as described, but the more useful change was structural: the scoring was extracted from the
inline body of `recommend_trips` into a pure function `score_post(post, signals, today) -> tuple[float, list[str]]`.
This is what makes the fix *testable at all* — an inline `date.today()` reads the host's timezone, which a test cannot
control, so the only way to assert the bucket was right would have been a `TZ`-manipulating end-to-end call. With the
clock handed in, six pure-rule tests pin the freshness tiers directly, and a seventh
(`test_the_caller_passes_a_utc_date`) asserts the source no longer contains `date.today()`. The split is deliberate:
the pure tests pin the rule, the source test pins the clock feeding it. Negative-validated: reverting to
`date.today()` reddens the source test while the seven pure-rule tests correctly stay green.

## 2. Frontend correctness

### F1 — Stale refresh token is reinstalled after an explicit session change `[read]` — **High**

**Where:** `frontend/src/lib/api.ts:47-50` and `:137-167`

```ts
export function setAccessToken(token: string | null) {
  accessToken = token;
  refreshInFlight = null;      // clears the *slot* ...
}

// ...but the pending attempt still runs to completion:
const attempt = (async () => {
  const res = await fetch(`${API_URL}${API_PREFIX}/auth/refresh`, {...});
  if (!res.ok) return false;
  const data = await res.json();
  setAccessToken(data.access_token);   // <-- reinstalls the OLD token
  return true;
})();
```

**Problem.** `setAccessToken` clears the in-flight *slot*, and the `finally` guard only clears the slot if it still
holds *this* attempt. Neither stops the `attempt` closure from **writing the token** when it resolves. So: logout
(or login as another user) while a refresh is in flight → the older refresh resolves → `setAccessToken(data.access_token)`
installs the **previous user's** token over the new session. The docstring explicitly claims this cannot happen
("a refresh that resolves after one of those must not reinstall the previous user's token"); it can.

Note this is *not* the race that the single-flight fix addressed — that fix correctly prevents replaying the cookie.
This is a second, independent hole one layer up.

**Fix.** Give the attempt an ownership token (a monotonically increasing generation counter set by `setAccessToken`)
and check it immediately before writing:

```ts
const gen = ++tokenGeneration;
// ...
if (gen !== tokenGeneration) return false;   // an explicit session change superseded us
setAccessToken(data.access_token);
```

The same guard should cover the failure path, so a superseded attempt cannot clear a *newer* token either.

### F2 — Old socket's `onclose` clobbers the new room's state `[read]` — **Medium**

**Where:** `frontend/src/app/chat/page.tsx:125-136`, cleanup at `:180-186`

**Problem.** The socket effect correctly uses `tRef` (honouring the documented WebSocket exception), but
`ws.onclose` / `ws.onerror` set state with **no check that they still belong to the current socket**:

```ts
ws.onclose = (event) => {
  setStatus("closed");                      // <-- clobbers the NEW room's status
  if (!openedRef.current) setNotice(...);   // <-- openedRef is shared across sockets
};
```

When the user switches rooms A→B, A's socket is closed by the cleanup and its `onclose` fires *after* B has already
set `connecting`/`open` — so B briefly (or permanently, if `openedRef` was true) shows "closed", and may show A's
error notice. `openedRef` being a single shared ref makes it worse: a stale close can read the *new* socket's
`openedRef`.

**Fix.** Capture the socket in a local and guard every handler:
`if (socketRef.current !== ws) return;` at the top of `onopen`/`onclose`/`onerror`/`onmessage`. Make `openedRef`
per-connection (reset in the cleanup) rather than a single shared ref.

### F3 — `profile` page: uncancelled fetch and unguarded history writes `[read]` — **Medium**

**Where:** `frontend/src/app/profile/page.tsx:78-80` (fetch), `:110-141` (`addHistory`), `:143` (`removeHistory`)

```ts
useEffect(() => {
  if (profile) void api.listHistories(profile.id).then(setHistories).catch(() => {});
}, [profile]);
```

**Problem.** Two separate issues. (a) `setHistories` is not guarded by a cancellation flag: `refreshProfile()` after
an avatar upload re-fires this effect, so two `listHistories` calls can be in flight and the **older** response can
land last and win — the visual equivalent of the bug `CityPicker` already solved with a request counter. (b)
`addHistory` and `removeHistory` have **no busy guard** — only `saveProfile` does (`disabled={busy}` at `:299`). A
double-click creates duplicate travel-history rows.

**Fix.** Adopt the request-counter pattern already used in `CityPicker` for the fetch; add a per-action busy flag (or
disable the button) for both history writes.

## 3. Design & architecture

**What is genuinely good, and worth not breaking:**

- **Layering is clean.** `api/` is thin routing + authorization; `services/` holds the reusable logic
  (`moderation`, `matching`, `notifications`, `content_filter`, `kv`, `storage`); `models/` + `schemas/` separate
  persistence from the wire. There is no business logic leaking into routers, and no ORM objects crossing the API
  boundary.
- **Degradation is a first-class, documented contract** on every external dependency. The three-part pattern
  (short timeouts → circuit breaker → documented fallback) is applied consistently in `kv.py`, `ws/pubsub.py`, and
  the rate limiters, and the *direction* of each degradation is reasoned about explicitly ("a wrong answer must be a
  larger quota / a smaller presence, never a failure"). This is the strongest part of the codebase.
- **The frontend i18n design is better than typical**: dictionaries are typed TS modules, not JSON, so `zh-HK` is the
  single source of the key set and **a missing translation is a compile error**. Locale in a cookie with no route
  segment is a real trade-off, made deliberately and documented.
- **Migrations are handled correctly** — backfill-before-drop, `server_default` on new NOT NULL columns, no
  dialect-specific types in downgrades.
- **Documentation is unusually rigorous** (`ARCHITECTURE.md` 1,298 lines, `SECURITY.md`, `STATUS.md`) and, more
  importantly, **auditable** — several sections record *measurements* and retracted claims, not just intent.

**Structural weaknesses:**

- **D3 [Medium] One invariant, several write paths, guarded in only one place.** This is the organising theme of
  B1/B3/B5. `accepted <= looking_for_count` is enforced under a row lock in `decide_application` but not in
  `PATCH /trips/{id}`; "one review per pair" is enforced by the DB for non-NULL trip ids but only by app code (and
  non-atomically) for NULL; "one block per pair" is enforced by a constraint the code does not handle. **A single
  invariant enforced from two places will diverge; it needs to be enforced from one.** Concretely: extract shared
  invariant helpers (capacity check, idempotent-upsert) and route every write path through them, and prefer a
  database constraint over an application check wherever the constraint can express it.
- **D4 [Low] Frontend pages are getting large.** `admin/page.tsx` 643, `profile/page.tsx` 509,
  `profile/[id]/page.tsx` 470, `chat/page.tsx` 455, `trips/[id]/page.tsx` 444 lines. Each mixes data fetching, local
  state, and presentation. There is no data-fetching library (a known recorded trade-off, tech-debt #7). At this size
  the cost is showing up as exactly the class of bug in F2/F3 — hand-rolled fetch/lifecycle bookkeeping that a
  library (or extracted hooks) would centralise. Consider extracting `useRoomSocket`, `useProfileData` hooks before
  adding another large page.

  **✅ Resolved (the two pages named in F2/F3).** `useRoomSocket` (`src/hooks/useRoomSocket.ts`) and
  `useTravelHistories` (`src/hooks/useTravelHistories.ts`) now own the fetch/lifecycle bookkeeping; `chat/page.tsx`
  and `profile/page.tsx` hold only state and presentation. The two hooks each absorb the guards from F2/F3, so the
  fix and the refactor are the same change rather than two divergent ones — and both F2 (10/10) and F3 (12/12)
  harnesses were repointed at the hooks and re-verified.

  One rule the refactor had to respect: callbacks and the resolver are read through **refs**, so the connection
  effect depends on `roomId`/`profileId` **only**. Adding `t` to that dependency list — the natural thing to do, and
  what `react-hooks/exhaustive-deps` would suggest — rebuilds the WebSocket on every language switch.
- **D5 [Low] `frontend/src/lib/i18n/dictionaries.ts` is 938 lines** holding two locales inline. It will keep growing
  linearly. Splitting per-feature (namespace files merged at the type level) would keep the compile-time safety while
  making diffs reviewable.

  **✅ Resolved.** 359 keys across 34 prefixes now live in **13 namespace files** under
  `src/lib/i18n/namespaces/` (`admin` 41, `auth` 32, `chat` 23, `city` 8, `common` 24, `enums` 7, `home` 20,
  `notifications` 30, `profile` 86, `reviews` 8, `server` 9, `tripDetail` 37, `trips` 34). `dictionaries.ts` is a thin
  composer using **spread syntax** (`...admin.zhHK, ...auth.zhHK, …`) rather than `Object.assign`, because spreads are
  checked for duplicate keys at the type level — a collision is a compile error, not a silent overwrite.
  `MessageKey = keyof typeof zhHK` and `en: Record<MessageKey, string>` keep a missing translation a compile error, so
  the safety property the monolith had is preserved exactly.

  `check:i18n` was extended to read the namespace files (its brace-walker was rewritten so a value containing `}` can
  no longer terminate the block early), to assert every namespace file on disk is imported by `dictionaries.ts`, and
  to exempt the namespace directory from the stray-literal scan while **including** `dictionaries.ts` in the reference
  corpus — excluding it would report all 359 keys as unused. A manual lossless diff against the pre-split copy
  confirmed no key was lost and no value changed.
- **D6 [Info] No automated concurrency in CI.** The `NullPool` + `httpx.ASGITransport` combination makes real
  concurrent requests *possible* in tests (the project has done this for #21), but there is no systematic pass. Given
  that B1/B2/B5 are all lost-race bugs, a small suite of "fire N concurrent identical requests, assert the invariant"
  tests would have caught them.

  **✅ Resolved.** `tests/test_concurrency_invariants.py` — one test per invariant (capacity, duplicate review,
  duplicate DIRECT room, block idempotency) plus a schema test, all following one documented recipe. Two rules are
  encoded in the file so the next invariant is added by copying the pattern:

  1. **`TestClient` cannot express a race** — its context manager serialises requests, so a "concurrent" test written
     with it passes against broken code. The race needs `httpx.ASGITransport` + `asyncio.gather` in a single loop with
     `NullPool` so two requests really get two connections.
  2. **Every test asserts both sides** — a liveness side (≥1 request succeeded, so the invariant cannot be "satisfied"
     by refusing everyone) *and* a safety side (persisted state honours the invariant). A status-only assertion passes
     if the refused write was already applied; a state-only assertion passes if every writer was rejected for an
     unrelated reason.

  Negative-validated **4/4**. Two lessons from getting there are worth keeping: my first attempt at the block mutation
  targeted the function's *pre-check* (`if existing:`) rather than the `IntegrityError` branch the race actually takes
  — i.e. the mutated line was **unreachable during a genuine race**, so it proved nothing. Retargeting it at the race
  path exposed a real hole in the test: it asserted only the block row count, never the audit row, so a
  `block_profile` that reported `created=True` for an existing row would pass. The assertion was strengthened to count
  `USER_BLOCKED` audit rows, and only then did the mutation go red.

## 4. Prioritised recommendations
