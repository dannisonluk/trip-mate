## 本階段完成的三個 P0

### 1. Refresh Token 撤銷 / 輪替 / 重用偵測
- `services/token_store.py`：`revoke(jti, ttl)` / `is_revoked(jti)` / `current_epoch(user_id)` / `bump_epoch(user_id)`
- `core/security.py::create_refresh_token(*, user_id, epoch=0)` 把 epoch 寫進 claim；新增 `token_remaining_seconds(payload)`
- `api/v1/auth.py::refresh` 順序很重要：**先查 reuse（is_revoked → bump_epoch → 401），再查 epoch，最後才 revoke 舊 jti 並簽新的**
- **為何要 deny-list + epoch 兩套**：deny-list 答「這個 token 失效了嗎」；epoch 答「這時間點之前簽的都失效了嗎」。
  沒有 epoch，reuse detection 就無法行動 —— 已輪替的 token 再出現時，無法分辨持有者是本人還是攻擊者，
  最安全是讓雙方都重登。
- `logout` 必須先 `revoke` 再清 cookie（否則登出只是客戶端假象）；`change_password` 呼叫 `bump_epoch()`

# 第四階段：Argon2 移出 event loop（清掉最後一項技術債）

## 觸發
使用者問「你好像遇到了一些問題」—— 其實是我探測指令寫錯（`anyio` 沒有 `__version__`），
但順勢把上一階段留下的技術債清掉。

## 先驗證前提：argon2 是否釋放 GIL
```
8 次雜湊 sequential: 0.27s (34 ms/op)
8 次雜湊 threaded  : 0.12s (15 ms/op)  → 2.27x
```
結論：**argon2 在 C 層釋放 GIL**，所以線程池不只是「不阻塞」，吞吐量也真的提升。
這點很重要 —— 如果不釋放 GIL，`to_thread` 只解決公平性，不解決吞吐。

## 實作
- `core/security.py` 新增 async 包裝：`hash_password_async` / `verify_password_async` /
  `verify_password_dummy_async`，內部用 `anyio.to_thread.run_sync`
- **同步原語保持公開**，因為 `app/seed.py` 等 CLI 腳本沒有 event loop 要保護
- Router 全部改呼叫 async 版本：`api/v1/auth.py`（register / login / change_password）、
  `api/v1/users.py`（註銷驗證 + 匿名化重設密碼）
- `config.py` 新增 `PASSWORD_HASH_MAX_CONCURRENCY: int = 8`
- `main.py` lifespan 設定 `to_thread.current_default_thread_limiter().total_tokens`

## 為何必須設線程池上限（容易忽略）
anyio 預設 **40** 條線程，而每次 Argon2 佔用 `memory_cost = 64 MiB` →
全滿峰值約 **2.5 GB**，足以讓小型容器 OOM。所以上限是**記憶體約束**，不是吞吐旋鈕。
預設 8 ≈ 512 MiB 峰值。注意是**每程序**上限，多副本時總並發 = 副本數 × 上限。

# 第六階段：標籤改 join table（P2 收尾）

## 做了什麼
`trip_posts.tags` 由 JSON 欄位改為 `trip_post_tags` join table
（複合主鍵 `(trip_post_id, tag)` + `ix_trip_post_tags_tag`），
新增遷移 `cafc59ae9ecc`（**先回填再刪欄**，降級可重建 JSON）。

**移除的真問題**：舊 `list_trips` 用 `limit(_TAG_SCAN_LIMIT=1000)` 撈到記憶體做集合交集，
超過 1000 筆時符合的貼文**默默消失**，而 `total` 看起來一切正常。

## 關鍵決策：半連接（IN）而非相關子查詢（EXISTS）
語意相同，但 SQLite **不會重排相關子查詢**，所以 `EXISTS` 不論標籤多冷門都要對
`trip_posts` 逐列做一次索引查找。50k 貼文 / 50k 標籤列實測（三次取最快）：

| 情境 | EXISTS | IN |
|------|-------:|----:|
| 冷門標籤（50 命中） | 57.9 ms | **0.1 ms** |
| 熱門標籤（50k 命中＝全表） | **57.0 ms** | 159 ms |

「用標籤篩選」本身就是為了縮小結果集 → 冷門標籤才是設計情境 → 選 `IN`。
代價：`IN` 會具體化命中的標籤列（記憶體非平坦）；單一標籤成長到數十萬列時要重評。
`EXPLAIN QUERY PLAN` 確認走 `LIST SUBQUERY` + `ix_trip_post_tags_tag`。

## 順手修掉的另一個真 bug：SQLite 根本不強制外鍵
`PRAGMA foreign_keys` 預設 **OFF**，且無法從連線字串開啟 → 所有 `ondelete=` 規則在
dev/test 方言上是**裝飾品**（刪行程不會連帶刪申請／通知），在 PostgreSQL 卻會。
已在 `app/db/session.py` 的 SQLite `connect` 事件中開啟；**Alembic 刻意不開**
（batch 重建資料表時外鍵必須關）。

最銳利的探針：`TripPost.applications` 是 `lazy="raise"` + `passive_deletes=True`，
ORM **永遠不會載入、因此永遠不會自行刪除**子列 —— 唯一能刪掉那列的就是 DB cascade。

## 其他實作細節
- `TripPost.tags` 改為 `@property`（讀）+ setter（寫），底層 `_tag_rows` 關係；
  關係用 `lazy="selectin"` **不是為了效能**，而是因為 `TripPostOut.model_validate()`

## 三個在寫測試時才發現的真 bug

1. **整個管理後台對所有人回 403（含管理員）。** `require_role("admin")` 的
   `user.role not in roles` 永遠不相等，因為 `UserRole.ADMIN`（`str` Enum）的值是
   **`"ADMIN"`**。三個管理端點全部鎖死。
   為何長期隱形：回 **403 而非 500**，前端把 403 當預期結果處理，
   而且**測試套件裡沒有任何管理員測試**（沒有 API 能授予角色，所以也沒人想過要建 fixture）。
   修法：兩邊正規化為大寫；**未知角色名稱在建立依賴時就拋 `ValueError`**
   （`require_role("admni")` 是同一種靜默全面鎖死，讓它在啟動時炸掉）。
   呼叫點改寫為 `require_role(UserRole.ADMIN.value)`，讓值不可能漂移。

2. **`REPORT_SUBMITTED` 的稽核紀錄悄悄丟失「檢舉原因」。**
   `detail={"reason": ...}` 被 `services/audit.py` 的提示清單命中 `"reason"` 而整個丟掉 ——
   但 `Report.reason` 是 `ReportCreate._valid_reason` 限制的**封閉 enum**，不是散文；
   真正該防的免費文字（`Report.detail`，上限 2000 字）本來就沒被複製進來。
   修法：移除 `"reason"` 提示，並**丟棄任何鍵時寫一筆 warning**。
   **會靜默失敗的警報器不算警報器** —— 這條教訓適用於所有「防護性」程式碼。

3. **`enum_col` 的 `length=20` 是定時炸彈。** 新增的 `REPORT_STATUS_CHANGED` 是 21 字元，
   SQLAlchemy 在 **mapper 設定階段**拋 `ValueError: length must be larger or equal than
   the length of the longest enum value. 20 < 21`，表徵是「應用程式無法 import」。
   修法：`length=max(20, longest)`（地板值確保既有欄位寬度不變，`alembic check` 驗證無漂移）。

## 測試踩到的三個 SQLite 細節（都會讓測試「假失敗」）
- **`Uuid` 欄位存成 32 位十六進位、沒有連字號。** 用 API 給的帶連字號 id 去下
  `WHERE id = ?` 會**永遠不匹配** —— fixture 會看起來有做事但其實沒升級到任何人。
  需要 `.replace("-", "")`。
- **`JSON` 欄位把 Python `None` 存成文字 `null`**（`none_as_null` 預設 False），
  所以 raw sqlite3 讀回來是字串 `"null"` 而不是 `None`。測試要 `json.loads`。
- **測試資料庫是整個 session 共用、只 `create_all` 從不 drop**，所以前一個測試寫的
  稽核列還在。斷言「恰好一列」的測試必須先清空（用 `sqlite_master` 檢查表是否存在，
  不要用 try/except 吞錯）。

## 給未來 session 的兩個操作教訓
- **同一個檔案不要在一個訊息裡發兩個 Edit。** 這次發生了兩次：工具**兩次都回報成功**，
  但只有一個真的落地（`deps.py` 的 `require_role` 主體、以及 `admin/page.tsx` 的

- **背景啟動伺服器時 `cmd1 && cmd2 &` 會把整串背景化**，於是後續指令仍在**原目錄**執行。
  這次因此讓 smoke 腳本在 repo 根目錄建了一個**空的** `smoke.db`，錯誤訊息
  `no such table: users` 看起來像應用程式的 bug，其實是腳本的路徑 bug。用絕對路徑。
