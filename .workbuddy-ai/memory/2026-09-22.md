# 第八階段：修掉三個真 bug + 內容審核

## 先說 bug（使用者要求「先修 bug 再做剩下的功能」）

用一個 subagent 掃 + 自己讀碼核實，找到並修掉三個**確定為真**的缺陷。
每一個都以「還原修正 → 對應測試必須失敗 → 還原成功」證明測試真的抓得住。

### 1. 評價授權只看「這一對人」，不看「這一趟行程」（最嚴重）
`_has_travelled_together(a, b)` 回傳的是配對層級的是非題（「這兩個人有沒有一起出遊過」），
但去重約束是 `(reviewer_id, reviewee_id, trip_post_id)`，而 `trip_post_id`
**由客戶端提供、從未驗證**。於是只要有一趟共同行程，就能**每次換一個行程 id**
無限刷評價 —— 包括掛在自己隨便開的行程上。正是該函式註解說要防的刷分。
為何原本測試沒抓到：它每次都重用**同一個** `trip_post_id`，而那條路徑確實會被去重擋下。
修法：`_shared_trip_ids()` 回傳**共同行程 id 集合**，要求 `trip_post_id` 必須在集合內；
`trip_post_id` 為 `NULL` 時另外用 `IS NULL` 去重（SQL 的 NULL 互不相等，
唯一約束在那條路徑上完全幫不上忙）。新增 `tests/test_reviews.py`（10 個測試）。

**可推廣的教訓**：「配對層級的授權檢查 + 客戶端可指定的範圍 id」＝ 可重放。
授權必須綁在**那個具體資源**上，不是綁在人與人的關係上。

### 2. 重複封鎖多寫一筆 `USER_BLOCKED` 稽核列
`moderation.block_profile` 是幂等的（已存在就回傳既有列），但 router 無條件寫稽核 ——
「封鎖一個已經封鎖的人」會在軌跡裡留下第二筆**從未發生**的事件。
而解除封鎖那半邊本來就有 `if removed:` 守衛，兩邊自相矛盾。
修法：`block_profile` 改回傳 `(block, created)`，只在 `created` 時記錄。

### 3. 封鎖後仍可讀取對方的評價
`GET /profiles/{id}` 與 `/histories` 對被封鎖者回 404（§1.3 不洩漏存在性），
但 `/profiles/{id}/reviews` 與 `/reviews/summary` 沒做同樣檢查，回 200 附資料。
順帶修好同前綴兩端點對 id 的解讀不一致（一個接受 profile id 或 user id，另一個只接受前者）。

## 接著做：內容審核（P2 最後一項之一）

`services/content_filter.py` + 接上全部 6 個文字寫入面
（行程 title/description、暱稱/bio、足跡 summary、評價 comment、聊天 REST + WS）。

### 核心設計：**誤擋比漏放更貴**
旅遊 App 的正常文字滿是會被粗略比對命中的詞：hotel **deposit**、
**killer** view、**kill** time、**Gunsan**、avoid tuk-tuk **scams**、**drugstore**。
所以本地規則刻意高精確度：只有幾乎沒有正當讀法的語句才 `BLOCK`，
可辯解的一律 `FLAG`（**放行**，只累加計數）。
`tests/test_content_filter.py` 用 25 句真實旅遊語料把「不得誤擋」鎖住。

### 實作時踩到、值得記下的三個點
1. **零寬字元要試兩種正規化。** 「移除」與「換成空格」各有盲點且互不包含：
   `pro\u200bstitute` → 移除才對（`prostitute`），`escort\u200bservice` → 換空格才對
   （`escort service`）。只做移除，第二類**整類繞過**（第一版就是這樣錯的）。
   `_variants()` 回傳兩種形式都比對。
2. **錯誤訊息不能說出命中的詞或規則**，只說欄位。說出來等於讓對方一次一條試出規則集。
3. **WS 與 HTTP 要分兩層 API**：`enforce()` 拋 422 給 HTTP；`screen()` 回
   `(verdict, detail)` 不拋，讓 WS 送可渲染的 `content_rejected` 錯誤框。
   （socket 上沒有 HTTP 狀態碼。）

### 供應商故障 fail-open（與限流器同一取捨）
供應商逾時／回錯 → 「無意見」，本地判定照舊。**fail-open 只適用供應商，不適用本地規則**：
供應商掛掉時 `escort service` 依然被擋。

### 被擋下的寫入**不進稽核表**
稽核表只涵蓋 spec 點名的四類；被拒寫入是高頻**運維訊號**，進指標與日誌就好。
理由與登入失敗不進稽核表完全相同：**不能讓重試的濫用者把唯一永不清理的表養大。**

# 第九階段：多語系 i18n（P2 最後一項）

## 做了什麼
`lib/i18n/` 兩支檔案 + 全站字串抽離：
- `dictionaries.ts` — **341 鍵 × 2 語言**（`zh-HK` / `en`）。`zh-HK` 是鍵集合的
  唯一來源，`MessageKey` 由它推導；`en` 宣告為 `Record<MessageKey, string>`，
  所以**缺一個鍵就是編譯錯誤**。
- `index.tsx` — `LocaleProvider` + `useI18n()`（`t` / `label` / `formatDate` /
  `formatDateTime`），locale 存 cookie，並同步 `<html lang>`。
- `components/Footer.tsx`、NavBar 的語言切換器。
- 抽離範圍：21 個檔案、約 340 行（11 個頁面 + 8 個元件 + lib）。
  **字典以外零漢字**（由 `npm run check:i18n` 驗證）。

## 關鍵決策與理由
1. **不用 `[locale]` 路由**（不用 next-intl 的標準做法）。locale 存 cookie，
   網址完全不動 → 12 個路由、所有連結、所有 E2E 斷言都不用改。
   代價寫進 `docs/ARCHITECTURE.md` §13：伺服器端 `metadata` 只能是預設語言，
   且首次載入非預設語言會短暫閃現預設語言。這是已登入產品，per-locale URL 價值有限。
2. **`errorMessage()` 的 fallback 改成必填**。`lib/api.ts` 不是 React 模組，
   拿不到 hook；留一個中文預設值就等於在共用模組裡留一句永遠不會被翻譯的字。
   每個呼叫點本來就知道該顯示什麼訊息（36 處全部都有傳）。
3. **列舉標籤用明確對照表**（`LABEL_KEYS`）而不是 `` t(`${group}.${value}`) ``：
   拼錯鍵名是編譯錯誤，而對照表查不到的值退回原始字串（醜，但不會變空白）。
4. **插入變數找不到時保留 `{name}` 原文**，不要清空 —— 清空會安靜地產生
   「你共有  則通知」；保留則看得見、能被回報。
5. **`<html lang>` 用 `zh-Hant-HK`，`Intl` 用 `zh-HK`** —— 這兩個不是同一個東西。
6. **多筆驗證錯誤的分隔符改用 `·`**：模組拿不到 locale，全形 `；` 在英文不對、
   半形 `;` 在中文彆扭，`·` 兩邊都自然。

## 防回退：`npm run check:i18n`（`scripts/check-i18n.mjs`）
`tsc` 只能保證「字典裡的鍵都翻譯了」，**看不到**從未搬進字典的字面值。所以另寫一支：
1. 走訪 `src/`，非 `dictionaries.ts` 的檔案出現**漢字**即失敗。
2. 檢查兩語言鍵集合相同、無重複鍵。

它只抓漢字（`U+3400–4DBF`、`U+4E00–9FFF`、`U+F900–FAFF` + CJK 標點 `U+3000–303F`），
**不含**全形符號區 `U+FF00–FFEF` —— 那區大半是標點，單獨一個 `；` 不是未翻譯的內容。
**這支腳本第一次跑就抓到一個真的漏網之魚**：`lib/api.ts` 用全形 `；` join 驗證錯誤。

## 踩到的坑
- **`送出申請` 被誤接成通用的 `common.submit`（=「送出」）**，
  導致 trip-flow 的兩條 E2E 逾時。**是 E2E 抓到的，不是 typecheck** ——
  因為兩者都是合法的字串，型別完全正確。教訓：抽字串時，
  共用鍵（`common.*`）只在**語意真的相同**時才能用；按鈕文案要專屬鍵。
- **Radix Popover 不會因為點了裡面的按鈕而關閉**。第一版切換器選完語言後選單還開著，
  我的 E2E 再點觸發器就把它**關掉**了，於是選項剛出現就被 detach。
  改成受控 `open` state，選完 `setOpen(false)`（順帶也是更好的 UX）。
- 寫「大規模取代」腳本時：**`s.count(old)` 不符就整支中止**會浪費一輪；
  改成收集所有失敗再一次回報（`failures` list），一次就能修完。
  另外**同一個字串在檔案裡出現兩次**（兩個 tab 共用的 markup）時，
  要嘛用 replace-all，要嘛用**行號**定位，不要靠縮排猜。

# 第十階段：補上兩個已知缺口（管理後台 E2E、ESLint）

P2 做完後，剩下的都是 P3（地圖，需合規圖資）與長期技術債。所以我改為關掉
**自己先前明確標記的兩個缺口**，而不是自行發明新範圍。

## 1. `scripts/manage_roles.py` —— 專案本來**沒有任何辦法建立第一個管理員**

這是一個真的維運缺口：沒有授予角色的 API，所以也沒有人能進管理後台，
這正是管理介面從來沒有瀏覽器測試覆蓋的**結構性原因**。

- 三個子命令：`list` / `promote <phone>` / `demote <phone>`。
- **刻意不做成 HTTP 端點**：能改角色的端點就是一個等著被設錯的提權路徑。
- 護欄：撤銷最後一位管理員需要 `--force`（否則等於把自己鎖在門外）；
  已刪除的帳號不能升為管理員（否則會做出一個登不進去的管理員）；
  每次執行都印出目標資料庫並**遮蔽密碼**（指錯 DB 就會在生產上授予 admin）。
- 14 個測試（`tests/test_manage_roles.py`），重點在護欄而非 happy path。

**踩到的坑**：第一版寫 `User.is_deleted.is_(False)` —— 但 `is_deleted` 是
`SoftDeleteMixin` 上的 **Python `@property`，不是欄位**，放進 WHERE 會在
建構查詢時就爆。要用 `User.deleted_at.is_(None)`。

## 2. `frontend/e2e/admin.spec.ts` —— 管理介面終於有瀏覽器覆蓋

3 條測試：一般使用者看不到管理後台、管理員處理檢舉、動作篩選。
管理員是用 CLI **現場升出來的**（`e2e/helpers.ts::promoteToAdmin`），
因為沒有 HTTP 端點可以改角色。

最有價值的一條斷言：稽核頁籤必須出現 **`from=open` / `to=actioned`** 的結構化細節 ——
這是唯一能從外部驗證「稽核軌跡真的記錄了它聲稱的東西」的方式。

### 這條測試抓到的事
第一次跑失敗，而**稽核紀錄自己說明了原因**：頁面上出現
`returned=0 status_filter=actioned` —— 表示我的 `getByRole("button", {name: "已處理"}).first()`
點到的是**篩選列**的按鈕，不是檢舉卡片上的動作按鈕（同一個標籤身兼兩職）。
所以狀態從未改變。修法：把點擊**限定在該筆檢舉的卡片內**。

### 順手修掉的重複
`resolvePython()` 在 `playwright.config.ts` 與 `e2e/helpers.ts` 各寫了一份，
結果 config 拿到 `E2E_PYTHON`、helper 沒有 → helper 退回沒有 sqlalchemy 的
`python`，只有需要升管理員的測試失敗。已抽成 `e2e/python.ts` 單一來源。

## 3. ESLint（`next/core-web-vitals`）

專案完全沒有 ESLint（`npm run lint` 會進入互動式設定流程）。安裝
`eslint@8` + `eslint-config-next@14.2.35`（Next 14 不能用 ESLint 9，那需要 flat config），
加上 `.eslintrc.json` 與 `.eslintignore`。

**首次執行就抓到 9 個 `react-hooks/exhaustive-deps` —— 全部是我在 i18n 階段引入的真 bug**：
把 `t(...)` 加進既有 `useCallback` 的函式體，卻沒有加進依賴陣列。
`t` 是**跟著 locale 改變的**，所以切換語言後那些 callback 仍握著舊的 `t`，
之後才產生的錯誤訊息會是**上一種語言**。型別完全正確，只有這條規則看得出來。

修法：8 處把 `t` 加進依賴；**chat 的 WebSocket effect 例外** ——
把 `t` 加進去會在每次切語言時拆掉重連 socket，所以改用 `tRef` 讀取
（永遠最新，且不重新訂閱）。

# 第十一階段：Deep Check（全面稽核）

用兩個 subagent 分頭掃（文件 vs 程式碼、死碼與契約漂移）+ 自己核實每一條。
**方法論重點：subagent 的每一條發現我都自己重跑指令驗證過**，因為其中一條建議

# 第十二階段：技術債 #4（CSP）—— 照著建議做了，然後用實測推翻它

## 背景
技術債 #4 一直寫著「建議改用 nonce-based CSP」。這一階段把它實作出來，
結果**證明這件事與本專案的靜態預渲染無法並存**，因此回退，並留下一道防護網。

## 過程與量測
1. 在 `src/middleware.ts` 實作 per-request nonce，`script-src` 改為
   `'self' 'nonce-xxx' 'strict-dynamic'`（移除 `unsafe-inline`）。
2. **E2E 15 條全綠** —— 完全看不出異常。
3. 對 production build 實測（非 `next dev`）：
   - 動態渲染 2 條路由：正常。
   - **build-time prerender 的 10 條路由：每張頁面 18 個 CSP violation。**
   - 且加 nonce 後 `'strict-dynamic'` 讓 `'self'` 對 script 失效，
     **連外部 chunk 檔案都被擋**，不只 inline script → 整頁不可用。
4. 全面回退，`next.config.js` 保留 `unsafe-inline` 並在上方寫明原因。
   `npm run build` 輸出可見 `○ (Static)` 10 條、`ƒ (Dynamic)` 2 條 —— 就是成因。

## 根因（可推廣）
**nonce 每次請求都不同，而預先渲染的 HTML 在建置時就產生完畢，結構上不可能帶上它。**
要嚴格 `script-src` 就得放棄預先渲染（改 `force-dynamic`，代價是每條路由每次請求
都伺服器渲染）。**這是二選一的架構取捨，不是可以順手修掉的 bug。**

## 留下的防護網：`npm run check:prod`
`frontend/scripts/check-prod.mjs` —— 自己起停 `next start`，用 Chromium 載入 7 條路由
（涵蓋靜態、動態、萬用字元），斷言 6 個安全標頭齊備、CSP 關鍵指令未被削弱、
**violation 為 0**，最後再驗一次 CSP 指令字串。

**已用人工注入的損壞 CSP 反向驗證會失敗**：注入 `script-src 'self'` 並移除
`X-Frame-Options` → 報出 **23 個問題、exit 1**，而且**獨立重現了原本的發現**
（`Executing inline script violates ... script-src 'self'`）。
驗證後已 `cp` 還原 `next.config.js` 並重建、重跑確認回到全綠。
> 又是同一課：**一個只會通過的檢查沒有價值**（與 `check:i18n` 死鍵檢查同源）。

## 為什麼這階段值得記
**這類缺陷只有 production build 看得出來。** `next dev` 每條路由即時渲染，
所以 E2E 永遠測不到 prerender 專屬的問題 ——
**「15 個測試全綠」與「10 條路由不可用」可以同時為真。**

**`next dev` 會用自己的 `.next` 蓋掉 production build。**

# 第十四階段：補上缺漏的 `.dockerignore`（映像檔洩漏密鑰）

Deep Check 掃過文件與程式碼，但沒掃**部署路徑**。這次補上：

## 問題
`backend/Dockerfile` 與 `frontend/Dockerfile` **都用了 `COPY . .`**，
但 repo 裡**沒有任何 `.dockerignore`**。實測後果：
- `frontend/node_modules/` **638 MB**、`frontend/.next/` **176 MB** 會被複製進映像檔，
  再被映像檔自己的安裝蓋掉 —— 既慢又製造「我這邊可以跑」的分歧。
- **更嚴重**：真實的 `.env` 會被**烤進映像層**。之後用 `RUN rm` 刪掉**沒用** ——
  `docker history` 依然看得到每一層。
  **`.gitignore` 保護 repo，但不保護映像檔** —— 兩者是獨立的防線，容易誤以為有其一就夠。

## 修法與驗證
新增 `backend/.dockerignore` 與 `frontend/.dockerignore`，
含 `!.env.example` 例外（**範本要進映像檔，密鑰不要**）。

**Docker daemon 在本機不可用，無法真的 build 驗證** —— 改用等效方式：
把 `.dockerignore` 當 `.gitignore` 放進暫存 repo，用 `git check-ignore --stdin` 逐條驗證。
結果符合預期：
- `node_modules/`、`.next/`、`test-results/`、`.git/`、`Dockerfile`、`README.md` → 排除
- `.env`、`.env.local`、`.env.production` → **排除**
- `.env.example` → **保留**（negation 生效，且贏過 `.env.*`）
- `package.json`、`src/`、`public/`、`requirements.txt`、`app/` → 保留

## 順手修掉的文件腐化（同類問題再現）
- README 專案樹**漏了 `test_manage_roles.py`**（14 個測試檔只列了 13 個）。
- README 樹中 frontend 區塊漏了 `.dockerignore`、`playwright.config.ts`、
  `scripts/check-prod.mjs`、`i18n.spec`/`admin.spec`、`e2e/python.ts` —— 全部補上。
- README 快速開始補上 `.dockerignore` 必要性的說明；
  `docs/SECURITY.md` 部署檢查清單新增一項，並寫明
  **「映像層一旦產生就無法撤回，唯一可靠補救是重寫歷史並輪換所有曾進入該映像的密鑰」**。

## 教訓
**Deep Check 也要涵蓋部署路徑（Dockerfile / compose / .dockerignore）。**
前幾輪只掃了 `app/`、`tests/`、`docs/`，於是「兩個 Dockerfile 都用 `COPY . .`
卻沒有 `.dockerignore`」這種顯而易見的高風險缺口一直沒被發現。
另外：**沒有 Docker daemon 不等於無法驗證** —— `.dockerignore` 與 `.gitignore` 同語法，
可以用 `git check-ignore` 做等價驗證，比「看過覺得對」可靠得多。

## 又找到一個真 bug：申請決策可以被覆寫，且 `looking_for_count` 從未被強制

`PATCH /trips/applications/{id}` 唯一的寫入是 `application.status = decision`，
**沒有任何狀態檢查**。用真實請求證實兩個後果：
```
第 1 次 decision=REJECTED -> 200 REJECTED
第 2 次 decision=ACCEPTED -> 200 ACCEPTED     ← 決策被翻轉
Bob 的通知：['APPLICATION_ACCEPTED', 'APPLICATION_REJECTED']  ← 互相矛盾
```
- **決策不是最終的**：被拒絕的申請人可以再被「接受」，同時收到兩則矛盾通知。
- **`looking_for_count` 形同裝飾**：schema 有 `ge=1, le=20`、也有落庫，
  但**沒有任何程式碼讀回它** → 建立者可在宣稱徵 1 人的行程上接受任意多旅伴。

為何既有測試沒抓到：它確實驗證了「非建立者 → 404」，但**那條分支在寫入之前就 return**，
所以那段變更從未被執行第二次。**這與技術債 #9 是同一種失敗模式**（唯一覆蓋的路徑提早返回）。

修法：已結案的申請不得改變決策（同決策重送視為幂等回 200、不重複通知；不同決策回 **409**），
接受前檢查 `already_accepted >= looking_for_count` 回 409。
**容量檢查刻意放在變更狀態之前**，被拒絕的接受不會留下部分寫入。
新增 `tests/test_applications.py`（3 個測試），並以「停用守衛（`if False and ...`）→
2 個測試必須失敗」反向驗證。**還原腳本用字串偏移切片會留下多餘的 `)`**（SyntaxError）——
改用語法保留的 `if False and ...` 取代，比切片可靠。

# 第十六階段：把「綠燈盲區」一次清掉（技術債 #21）

第十五階段評估的結論是「**綠燈會掩蓋壞行為**」是這個專案的結構性風險，
#9 與 #20 都源於同一模式。所以這一階段不再修單一 bug，而是**系統性核對全部 29 個寫入端點**。

## 這個模式的精確定義（值得當成專案的固定檢查項）

> 唯一覆蓋該端點的測試，走的是**在寫入之前就 `return`** 的分支
> （「非擁有者 → 404」「被封鎖 → 404」「型別不對 → 400」）。
> 於是那段變更**從未被任何測試執行過**，端點可以完全壞掉而測試全綠。

核對方法：對每個寫入端點，要求存在一條斷言**成功狀態 ＋ 可觀察的寫入效果**
（重新讀取、或對**位元組**斷言）的測試。**只斷言狀態碼不算數。**

## 找到 4 個真正的盲點（29 個中）

| 端點 | 原本的覆蓋 | 未執行的程式碼 |
|------|-----------|---------------|
| `POST /uploads/image`（成功路徑） | 唯一測試送 SVG 斷言 400 | `store_image`／Pillow 重編碼／`build_key`／`_put_local` **全都沒跑過** |
| `DELETE /profiles/me/histories/{id}` | 零覆蓋 | 刪除是否落庫、擁有權檢查是否生效 |
| `POST /profiles/me/upload-url` | 零覆蓋 | 錯誤是否為 400 而非 500 |
| `POST /uploads/presign` | 零覆蓋 | 兩道守衛都未被釘住 |

**判斷方式**：派出一個 Explore subagent 逐條讀測試**body**（不看測試名稱），
我再自己用 `grep` 核實它的結論。subagent 認為 25 個有 happy path（其中 `register`
與 `create_trip` 由 fixture 驅動 —— 有執行但未斷言回應內容），4 個是盲點，**與我核實一致**。

## 新增 `tests/test_upload_and_history_writes.py`（11 個測試）

最值得記的是 **EXIF 那條**。`storage.py` 的 docstring 宣稱「重編碼會抹除全部 metadata
（含 EXIF GPS）」—— 這是核心私隱承諾，但**從來沒有任何測試驗證過**，
而且 `201` 本身無法區分「已抹除」與「原樣存回」。測試因此：

1. **先斷言 fixture 真的帶有 EXIF** —— 否則測試會在「檔案本來就沒 metadata」時
   假通過。這是「只會通過的檢查」的另一種變體（與 `check:i18n` 死鍵那次同源）。
2. 上傳後**從磁碟按 `LOCAL_UPLOAD_DIR` 找出該物件**，解析其 EXIF 斷言標籤全消失。
3. 同時 assert **它仍是一張可解碼的圖** —— 否則「沒有 EXIF」可以靠
   「檔案被截斷成零位元組」而通過。

## 順帶查出的結構性事實：`presign_put` 的白名單在 HTTP 層不可達

```python
if settings.STORAGE_BACKEND != "s3":        # ← 先執行；local 後端在此就 400
    raise UploadError("Pre-signed uploads require the S3 storage backend.")
if content_type not in ALLOWED_MIME:        # ← local 後端下永遠到不了
    raise UploadError("Unsupported content type.")
```

`STORAGE_BACKEND` 在 dev／test 預設是 `"local"`，所以第一道守衛**必定短路**，
**content-type 白名單在測試環境中永遠不被求值**。

**關鍵洞察**：這是「覆蓋率」指標的典型盲區 —— 那幾行有被 import、有被執行到函式，
所以覆蓋率會顯示「已覆蓋」，但**在測試環境裡它從未被求值**。把它整段刪掉不會有任何測試變紅。
而它正是生產環境上**唯一**阻止 `application/pdf`（或呼叫端任意命名的型別）
被寫入上傳桶的檢查。

處理方式：**直接呼叫 `presign_put` 並暫時把 `STORAGE_BACKEND` 切成 `"s3"`**
（`generate_presigned_url` 是**本地簽章**，不需真憑證也不會連 AWS，
所以「允許的型別會回傳 URL」本身就是白名單放行的**正面訊號**）；
HTTP 層則只斷言「local 後端下一律是那個 400」。

> **可推廣的規則**：當一段安全檢查被另一段較早的檢查**在測試環境中永久遮蔽**時，
> 它需要一條**直接呼叫該函式**的測試。否則它是程式碼意義上的裝飾品。

## 反向驗證（這次的工具教訓很重要）

目標是「停用四道守衛 → 恰好對應的 4 條測試失敗」。踩到的坑：

- **`cat > /tmp/x.py` + `python /tmp/x.py` 在 Windows Git Bash 下失敗** ——
  Git Bash 的 `/tmp` 與 Python 認知的 `/tmp`（→ `C:\tmp`）**不是同一個目錄**。
  備份檔要放在**專案目錄內**（`_bak_profiles.py`），不要放 `/tmp`。
- **heredoc 寫的替換腳本，anchor 字串含縮排時極易不匹配**（第一次 `assert count == 1` 就
  回報 `0`）。改用 `Write` 工具寫成正式腳本、並在每個替換前 `assert count == 1`，
  一次就過。**別用 `Bash` + heredoc 寫多行 Python 替換腳本。**

結果：停用四道守衛後 **恰好 4 條失敗、其餘 7 條通過**；`--restore` 還原後
`diff -q` 確認與備份**逐位元組相同**，11 條全綠。
