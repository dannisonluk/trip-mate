### 關鍵教訓

- **`feature_code` 不在 `CityOut` 裡**（刻意不暴露）。測試要用**可觀測後果**
  （country_code 順序 + population 反轉）斷言，不能斷言內部欄位。
- **`name` 是最後一個 tie-breaker，但種子裡沒有「人口相同」的列** ——
  所以移除 `City.name.asc()` **不可能**被任何測試抓到。我一度寫了
  `test_name_breaks_population_ties` 假裝有釘住，後來**誠實改名**
  為 `test_same_name_is_ranked_and_stable`（只驗證跨請求穩定）並
  **從突變清單移除該 case** —— 不可觀測的守衛不該留在清單裡充數。
- **`PPLA%` 的大小寫在 SQLite 上不可測**：`SELECT 'PPLA2' LIKE 'ppla%'` → 1
  （SQLite 的 `LIKE` 對 ASCII 折疊大小寫）。所以「把 pattern 改成小寫」
  這個突變在 SQLite 上**永遠不會**變紅，該 case 已從清單移除並註明只在 PG 可測。
  **不要留一個註定失敗的 case，那會讓整份報告的說服力歸零。**
- **測試檔改動後要同步改突變腳本的 selector**，否則會出現
  「測試不存在 → pytest 收集失敗 → 誤判為 RED」。
- 排除 bytecode 快取後仍失敗時，**要直接查 DB 檔內容**而不是猜。
  這次先誤以為是 `delete(City)` 沒生效，實際查 DB 才發現列都在、
  是**我的斷言假設了錯誤的排序**。

### 三個真 bug（全部是我造成、或我沒看見的）

**1. 手動起後端漏了 `BACKEND_CORS_ORIGINS` → 17 個 E2E 全紅。**
`config.py:42` 預設是 `http://localhost:3000`，而 E2E 前端在
`http://127.0.0.1:3099`。preflight 被拒（`400`、**沒有 `access-control-allow-origin`**），
於是每一個帶 `Authorization` 的請求都被瀏覽器擋下。表徵極具誤導性：
登入頁顯示「登入失敗，請稍後再試。」（通用 fallback）而不是 "Invalid credentials"，
看起來像「RBAC 壞了」。
> **診斷法**：直接對活著的後端發 preflight，看回應有沒有 ACAO：
> `curl -X OPTIONS .../api/v1/auth/register -H 'Origin: http://127.0.0.1:3099' -H 'Access-Control-Request-Method: POST' -D -`
> 有 `access-control-allow-methods` 但**沒有** `allow-origin` ⇒ 來源被拒。

**2. refresh token 的「重放偵測」+ 前端沒有 single-flight ⇒ 並行請求會把使用者登出。**
`auth.py::refresh` 每次成功都**撤銷**舊 token；再次出示已撤銷的 token 被視為
盜用 → `bump_epoch` → **所有 session 失效**。
實測（同一 cookie 三個並行請求）：**1×200、2×401**。
而 `tryRefresh()` 原本每個呼叫者各發一次 ⇒ 任何發出多個並行認證請求的頁面
（行程詳情同時打 `trips/{id}`、`notifications/unread-count`、`profiles/me`、`auth/me`）
在慢網路上就會把使用者登出。
修法：`lib/api.ts::tryRefresh` 加 **single-flight**（共用同一個 in-flight promise），
並讓 `setAccessToken` 清掉它（明確的 session 變更不得被舊 refresh 覆寫）。

**3. `globalSetup` 從不重置 `e2e.db` ⇒ 測試行為是它自己歷史的函數。**
`create_all` 只建表、永不 drop，DB 檔跨次累積（實測累到 **119 users / 42 trips / 52 audit_logs**）。
`稽核紀錄可以依動作篩選` 斷言「篩到沒人做過的動作要顯示空狀態」，
但列數長大到超過 `AUDIT_PAGE_SIZE=25` 之後，斷言其實在測一個有分頁的非空列表。
修法：`globalSetup` 刪 `e2e.db`（連 `-wal`／`-shm`，否則 SQLite 會復原舊內容）。
> **順序陷阱**：Playwright 的 `globalSetup` 在 `webServer` **之前**跑，
> 所以正常路徑下刪檔是安全的；但 `E2E_NO_WEBSERVER=1` 時後端已開著舊檔，
> 刪掉會讓後端寫到已 unlink 的 inode。故該模式下**跳過刪除、仍跑 seed**。

### 我自己造成的測試碼 bug

- **`getByText("Tokyo")` 變成 strict mode violation（2 個元素）**：
  我在 `CityMapLoader` 加了一個 `sr-only` 的 `fallbackLabel`（`"Tokyo Japan"`），
  與地圖的 `aria-label`（`"Tokyo, Japan"`）重複。
  但**表頭本來就已經有城市＋國家**，這個 sr-only 是冗餘的 →
  直接**刪掉 `fallbackLabel` prop**（連同呼叫點），一次解決歧義與死參數。
  斷言改為 `getByRole("img", { name: "Tokyo, Japan" })`（`CityMap` 是 `role="img"`）。
  > 通則：**在地圖上疊一個視覺隱藏的文字副本，會讓所有 `getByText` 變歧義。**
  > 有 `aria-label` 就夠了。

### 負向驗證的誠實結果（重要）

- **`AuditTrail` 的 out-of-order guard：0/3 釘住。**
  我加了 `requestId` ref（沿用 `CityPicker` 的樣式），但把三個 guard 逐一停用
  **測試都仍然全綠** —— 因為 localhost 上兩個回應都在數毫秒內回來，race 從不發生。
  我**沒有**把它當成修好的證據：保留程式碼但把「未釘住」寫進註解，
  並在該 guard 的說明裡註明它**不是**那次 E2E 失敗的原因。
- **single-flight guard：4 次重跑仍綠 ⇒ 判定 inconclusive。**
  但這次有**直接證據**：curl 三個並行 refresh 得到 `1×200 + 2×401`，
  證明後端的失效模式真實存在，guard 針對的就是這個。
  > 教訓：**當競態在測試環境不可觀測時，改用「直接對 API 重現失效模式」來證明**，
  > 而不是靠 E2E 擲骰子。

### 更正 1：`AuditTrail` 的 out-of-order guard **確實**是那次 E2E 失敗的原因

上一階段寫「0/3 釘住，且它**不是**失敗原因」。第二句是**錯的**，而且是我自己

DB 確認 `REPORT_STATUS_CHANGED` 存在，而 DOM 只有 3 列不含它 ——
**這正是典型的過期回應覆蓋**。guard 是對的，加它是對的。

### 更正 2：負向驗證量到 1/3，原因是**方法錯了兩次**，不是行為沒被釘住

| 嘗試 | 做法 | 結果 | 為什麼錯 |
|------|------|------|----------|
| 1 | 停用 guard、跑整套 | **1/3** | 賽跑**取決於時序**。沒有延遲時舊回應通常不最後落地 → 突變**不可觀測** |
| 2 | 加 E2E，只斷言「篩選後清單為空」 | 停用後**仍綠** | 斷言**什麼都沒釘住**：新回應落地時畫面本來就是空的 |
| 3 | 對被篩選的請求加 route 層 1200 ms 延遲，**同時**斷言「新列出現」與「舊列消失」 | **見下** | — |

> **通則（這條要記住）**：突變測試只對**決定性**行為有效。
> 對時序相依的賽跑，**延遲才是讓突變可觀測的東西**；而斷言必須同時涵蓋
> 「新狀態成立」**與**「舊狀態被拒絕」兩側，否則會寫出一個永遠通過的測試。

`only-loading-guard` 在第一次跑就已釘住（20 passed / 1 failed）—— 每次 `load()`
的 `finally` 都清 `loading`，舊請求回來時會把新請求的 spinner 弄掉，是**決定性**的。

### 另外兩件事

- **`__Host-` cookie 前綴不可用**：它要求 `Path=/` **且不得有 `Domain`**，
  而 refresh cookie 的 `path` 刻意收窄到 `/api/v1/auth` → **規範上不相容**。
  要換就得把 path 放寬為 `/`，等於放棄 CSRF 縮小暴露面的設計，
  只換到「防誤設 `Domain`」這個**啟動期 validator 就能達成**的保證。
  `COOKIE_DOMAIN` 為空（host-only）才是現行的正確設定。已寫進 SECURITY.md §1.1。
  > 未實作：**沒有任何地方驗證 `COOKIE_DOMAIN` 為空** —— 生產填了就靜默失去保證。
  > 應在 `core/config.py` 加 validator，`ENVIRONMENT=production` 且非空時**啟動即失敗**。
- **`reactStrictMode: true` 是**唯一會**產生那對重複請求的解釋**。曾考慮過
  Next dev 的雙重 render（不觸發 effect，故不成立）、以及條件式第二次請求（不存在）。
- **不要把未啟用 JS 的爬蟲當成「執行不會發生」的證據**：`RequireAuth` 在
  `loading` 時會呼叫 `tryRefresh()` → `POST /api/v1/auth/refresh`，
  所以 `/trips/<id>` 的預渲染 HTML 仍會發請求。`check:prod` 因此**確實會**
  走進 trip-detail 頁與地圖分支（`img-src` 是 `'self' data: blob: https:`，圖磚不受阻）。
