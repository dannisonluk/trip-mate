### B. WebSocket Redis Pub/Sub 扇出（#6 的主要缺陷）

**新增** `app/ws/pubsub.py`；**改寫** `app/ws/manager.py` 的 `broadcast`；
**接線** `app/main.py` lifespan。

#### 設計要點

| 決策 | 理由 |
|------|------|
| `broadcast()` = 本地投遞 **+** 發布；`deliver_local()` = 只本地 | 若 `on_remote_frame` 呼叫 `broadcast`，兩副本會**無限互轉**同一則訊息 |
| transport **注入** `ConnectionManager(transport=…)` | 原本硬參考模組 singleton，導致無法在不 patch module globals 的情況下測試 |
| `instance_id` **可注入**，非直接讀模組常數 | 同行程兩個 transport 若共用 id 會互丟對方訊息當自己的回音 |
| `exclude` **隨訊息跨副本**，由持有 socket 的副本套用 | 否則發送者的 socket 落在別的 worker 時，會看到自己的 typing（`--workers N` 分配非決定性 → **間歇性** bug） |
| 降級決定用 **`publish()` 回傳值**，不是 `enabled` | `enabled` 是不碰網路的**預測**；冷啟動且 Redis 掛掉時仍讀 `True` → warning **永不觸發** |
| 降級時**本地投遞照常** | 否則 Redis 故障升級為**總聊天故障** |
| `start()` 短暫等（≤0.5s）訂閱建立 | 讓「正在監聽」與「還沒開始」**可被區分**；`subscribed`（事實）≠ `enabled`（預測） |
| `_listen_forever` 是**迴圈** | 掉訂閱後副本照樣收 socket、照樣發布但收不到 → 「看起來健康卻半聾」 |

#### 過程中修掉的三個真 bug

1. **信封雙層巢狀**：`publish()` 原本把傳入的 dict 再包一層 `{"payload": …}`，
   而 manager 已傳 `{"payload":…, "exclude":…}` → 接收端拆到錯誤的層。
   修法：`publish()` 把 frame **原樣**放進 `payload`，不重複包裝。
2. **`asyncio.Event` 在 import 時建立** → 綁定到第一個 loop。
   模組 singleton 在 **import 期**建構（此時無 loop），TestClient 每個測試新 loop
   → **95 個錯誤**：`is bound to a different event loop`。
   修法：Event 改在 `start()` 內建立（一定有 live loop），型別改 `asyncio.Event | None`。
   > **通則**：任何持有 loop 相關物件的東西都不能在 import 期建構。
3. **`enabled` 語意錯誤**（見上表）。

#### 測試（`tests/test_ws_fanout.py`，8 個）

用**行程內 broker** 取代 Redis（此環境無 Redis 服務），兩個 manager 各自持有 transport。
足以釘住**我們的邏輯**；**不足以**證明 Redis Pub/Sub 本身可用。

- **fake 第一版錯了**：把 `psubscribe("prefix*")` 當**精確比對**，於是每條跨副本測試都失敗，
  而生產程式碼其實是對的。
  > **通則：一個不模擬被取代物語意的 fake，測的是 fake。**
- **交付是非同步的**：`await broadcast()` 返回時其他副本**尚未**投遞完成（listener task 要排程）
  → 測試需 `_settle()` 讓出執行權。這是**設計的性質**，不是測試瑕疵：
  產品程式碼不得依賴「廣播返回即已送達」。

## 已重現（硬證據）

1. **B1 重複 review → 永久 500**。`reviews.py` 用 `.scalar_one_or_none()`；`trip_post_id` 可為
   NULL 而 SQL 的 NULL 互不相等 → `uq_review_once_per_trip` 對 NULL 無效 → 兩列匹配 →
   `MultipleResultsFound` → 未捕捉 → 500，**且永久無法恢復**。
   重現法：直接植入兩列 `trip_post_id IS NULL`（= 輸掉的競態留下來的狀態），再打一次 endpoint。
   log：`unhandled_exception {"exception_type": "MultipleResultsFound"}`。
   修法：`.scalars().first()`（止血）**＋** partial unique index
   `WHERE trip_post_id IS NULL`（真正堵住）。兩者都要。

2. **B3 `PATCH /trips/{id}` 可超收**。`TripPostUpdate` 同時暴露 `looking_for_count` 與 `status`，
   handler 直接 `setattr` 迴圈，**不重查已 ACCEPTED 數**。accept 路徑（`trips.py:307`）在無條件
   列鎖下小心防守此不變式，這個端點卻繞過去。
   重現：limit 3→1 而有 2 位已接受 → **200 OK**，行程永久超收（limit 1 / accepted 2），
   且**沒有任何端點能修**（accept 一律 409）。`status` 亦可設成任意 enum 值。

3. **B2 DIRECT 房間可重複建立**：`chat_rooms` 只對**成員**有 unique，pair 本身無約束
