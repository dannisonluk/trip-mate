## ⚠️ 三個代價很高的教訓（都寫進 ARCHITECTURE.md §16.8）

1. **同一行程的兩個物件不是兩個副本。**
   第一版測試用「兩個 `ConnectionManager`」建模兩副本 → **5 個突變全綠、等於沒釘住**。
   因為兩者**共享模組全域 `_memory`**，連「每副本 dict」都看起來共享。
   正解：副本 = 各自獨立的 `kv` 模組（`importlib.util.spec_from_file_location`
   從同一原始檔載入，各自一份全域）。**副本是兩個行程，不是兩個物件。**

2. **patch `_redis` 會繞過斷路器。**
   斷路器檢查就在 `_redis()` 內。要驗斷路器，必須 patch **更低一層**的
   client class（`redis.Redis.from_url`），讓真的 `_redis()` 留在路徑上。
   同理：**建構失敗 ≠ 執行期失敗** —— `from_url` 拋會設 `_redis_disabled=True`
   （永久停用），於是重試停止的理由與斷路器無關，測試會在斷路器被移除後照樣通過。
   要用「client 建得起來、`pipeline()` 拋」來測斷路器。

3. **`conftest.py` 把 `RATE_LIMIT_ENABLED` 設 false**，`_redis()` 在限流關閉時直接短路。
   沒打開就跑，會斷言到「0 次重試」→ **看起來像斷路器完美運作，其實 Redis 從未被查詢**。

# 2026-09-26（第二十五階段）— 多副本前置清單 #8／#21／#22a／#22b 全部結案

## 一句話

**#8/#21/#22a/#22b 與 #3 同源：某個量測是「每行程」的，但它要描述的對象是「整個部署」。**
單副本時它恰好等於全域上限 —— 這就是它們能長期存活且沒有測試的原因。

## 共用原語

`services/kv.py::DistributedSemaphore` — 許可證存在 Redis 一個 key 上，`INCR` 後才判斷
（**不是** read-then-write：那會讓兩個副本都讀到 `limit - 1`）。
**TTL 是洩漏閥，不是過期語意**：持有許可的副本死掉就不會 `DECR`，
key 會棘輪到「永遠滿」；每次 acquire 刷新 TTL 讓被遺棄的 key 自然老化，上限自癒。

## 四個修正

- **#8 雜湊池**：`PASSWORD_HASH_MAX_CONCURRENCY` 是**記憶體預算**不是吞吐旋鈕
  （`memory_cost=64 MiB`／次，真實峰值 = `8 × 副本 × 64 MiB`）。
  兩道上限且**不可互換**：anyio thread limiter 是**每行程**（Redis 掛掉時的最後防線），
  `DistributedSemaphore` 是**全域**。**失敗方向必須是「額度變大」，不是「功能壞掉」**：
  拿不到許可 → 等 2.5 秒後**不計數放行**，永不拒絕登入。
  啟動要 log **算式**（不是設定值 —— 設定值永遠看起來正確）。
- **#21 TOCTOU**：兩層，缺一不可。
  ① 容量檢查**之前**取序列化鎖；② `UPDATE ... WHERE status='PENDING'` 用 `rowcount` 仲裁。
  鎖擋「兩個**不同**申請同時通過容量檢查」；CAS 擋「**同一**申請被決定兩次」。
- **#22a 斷路器**：`_BreakerState` 預設行程內，`set_breaker_backend()` 是選用接縫。
  **斷路器是 publisher，不是真相來源** —— 需要 Redis 才知道 Redis 掛了的斷路器比沒有更糟。
  只在啟動 `ping()` 成功後才裝（死 Redis 開機不該讓每次讀取都付連線嘗試）。
- **#22b seed**：`pg_advisory_lock` 固定 key；SQLite **誠實 no-op**，不做假的保證。

## ⭐ 本階段最重要的兩個發現（都是「我的測試在說謊」）

### 1. 列鎖原本只掛在 ACCEPTED 分支，REJECT 完全不設防

原本列鎖寫在 `if decision == ACCEPTED:` **之內**（因為只有容量檢查需要它）。
`NullPool` 讓每個請求各有自己的連線 → ACCEPT 與 REJECT 都讀到 `status == PENDING`
→ 都走到 CAS → **後寫的勝出**。

實測（`probe_cas.py`，12 輪）：**2/12 出現 `codes=[409, 200] final=['REJECTED']`**
—— ACCEPT 回報 409、資料列卻是 REJECTED，即 accept 宣告成功卻不持久。

修法：列鎖提到分支**之前**，兩個決定共用同一把鎖。

### 2. 突變 I 曾被報成 PINNED，其實是 flake

`test_concurrent_contradictory_decisions_on_one_application` 原本斷言
**「同時發出的 ACCEPT 一定贏」**。兩個請求同時發出，**勝負由排程器決定**，
沒有任何機制規定誰先 —— 這是**斷言了一個不存在的順序保證**（實測 ~17% 是 REJECT 贏）。

它同時解釋了突變 I 的假 PINNED：E 那一列報的 `1 failed` 是這個 flake 偶然造成的，
跟 E 的突變無關。**一個 flaky 測試會讓整份突變報告的數字失去意義。**

修法：斷言**不變式** —— 只有一個贏、資料列等於**贏家**的決定、輸家被告知輸了。
修後 15/15 穩定；突變 I 重跑 **8/8 全紅**。

# 2026-09-26（第二十六階段）— #6 presence 結案（多副本前置清單真正全清）

## 做了什麼

`ConnectionManager.online_profiles` 過去只能回答「連到**本副本**的人」。N 副本下房間
名單只報出一半，**哪一半還取決於負載平衡器** —— 不是不完整而已，是**不確定**，而且
不拋任何錯誤。

修法在 `services/kv.py::PresenceRegistry`：

```
tripmate:presence:{room}:{replica}  ->  "profile_a|profile_b"   (TTL = stale_after)
```

每副本一個 TTL 條目 + 心跳刷新；讀取是未過期條目的**聯集**。

## 三個關鍵設計決定

1. **不是共享 SET**。被 SIGKILL 的副本永遠不會呼叫 `disconnect`，它的成員會永遠留在
   集合裡，而且系統**無法分辨鬼影與安靜的真人** —— 沒有任何簿記能救，因為要記的資訊
   根本沒被產生。存活語意只能由副本自己提供。
2. **心跳重寫整份名單**（`delete`+`sadd`+`expire` 一個 pipeline），不只延長 TTL。
   這才是聯集讀**自我修復**的來源：漏掉的 `leave` 被下一次心跳覆蓋。只延長 TTL 的話，
   那個成員會被每次後續心跳持續續命、永遠不消失。
3. **`online_profiles` 改為 `async`**（刻意）。呼叫端不應該有能力把「本副本的切片」
   誤當成整個房間。`is_member_online` 則**刻意保持同步、本副本語意** —— 它回答
   「我能不能投遞」，是關於本行程的路由問題，與 presence 是兩個不同的問題。

## 明文取捨

心跳停頓 > `stale_after`（45s vs 15s）時成員短暫消失。**刻意**：短暫**缺席**是外觀
錯誤，永久**鬼影**是正確性錯誤。

降級契約：Redis 不可用 → 退回本副本名單（= 修之前的行為），**少報，不失敗**。
presence 永不拋錯 —— 它跑在聊天熱路徑，每次 join/leave 都呼叫。

## 附帶修掉：心跳任務洩漏

交出 presence 後 `-k "ws or room or presence"` → 33 passed 但 **6 個
「Task was destroyed but it is pending!」**，全指向 `_heartbeat_loop`。
`test_ws_fanout.py` 每個測試 `asyncio.run()` 自建 manager、從不呼叫 `shutdown()`。

兩層修法（缺一不可）：
1. 迴圈在最後一個房間清空時**自行結束**（`_beat_once()` 回 `False`）。
   「有人記得呼叫 `shutdown()`」不是保證 —— 測試直接建 manager 永遠不會呼叫它。
2. 心跳**預設關閉**（`heartbeat_enabled=False`），只有 app singleton 明示開啟。
   背景計時器只對長命伺服器有意義。

修後重測：**33 passed、0 個 Task was destroyed**。

## 測試與負向驗證

`tests/test_presence_registry.py`（17 個測試）。副本用 `importlib` 從同一原始檔載入
獨立 `kv` 模組（各自 `_memory`／`_redis_client`／`_breaker`，只共享假 Redis）。

假 Redis 需要**真的 TTL 模型** + set ops，所以 `FakePresenceRedis` 帶一個可推進的
`_TestClock` —— 鬼影驅逐與 TTL 刷新都靠 `clock.advance()` 測，不用 sleep。

`mutate_presence.py` → **10/10 PINNED**：移除聯集、`join` 不設 TTL、`leave` 刪整個房間鍵、
心跳只延長 TTL、心跳不刷新 TTL、shutdown 不清理、presence 改為拋錯、manager 只讀本地、
`connect` 不寫、`disconnect` 不清。

## ⚠️ 這一輪最貴的一課：用被測物件的「順路輸出」驗證它 = 什麼都沒驗證

突變 I（`connect` 不寫 presence）起初 **NOT-PINNED**。測試是：

```python
await manager.connect("room-1", "profile-a", ws)
assert await manager.online_profiles("room-1") == ["profile-a"]   # ← 假的
```

`online_profiles` 回傳 `presence.online(local=self.local_profiles(...))`，
而 `local_profiles` 讀的就是 socket 表 —— `connect` 放進去的。所以**本副本的讀取光靠
socket 表就會回傳該成員**，把 `join` 整段拿掉測試照樣綠。

修法：改由**另一個副本**（`replica-observer`，手上沒有任何 socket）觀察。

> **要驗證一個寫入，就要從看不到本地狀態的地方讀。**

這是 §16.8「同一行程的兩個物件不是兩個副本」的**鏡像**：那次是假副本讓測試假通過，
這次是**假觀察者**讓測試假通過。

## 本節（B7 / B8 / B9 / D4 / D5 / D6）的技術要點

### B7 — 跨副本 breaker 的時鐘安全
`monotonic()` 沒有跨行程共同 epoch，所以**發布絕對值**是錯的。修法是把
「發布端」與「讀取端」各自做對：發布 `deadline = time.time() + _COOLDOWN_SECONDS`
（欄位名 `deadline`，舊的 `cooldown_until` 欄位已移除）；讀取時把 wall clock
換成**時長** `remaining = float(published) - time.time()`，再鉗到
`min(remaining, _COOLDOWN_SECONDS)`；`self.cooldown_until` 保持 **monotonic**，
只與 `time.monotonic()` 比較。負 `remaining` 跳過；非數值忽略而非拋錯。
測試用 monkeypatch 把跟隨者的 `time.monotonic` 偏移 −6 小時，證明採納不再依賴共同 epoch。

### B8 — 每個改狀態的端點都要限流
報告說 5 個 DELETE 無限流；用**路由盤點測試**（讀 `app.routes`）代替人手核對後
多找到 **5 個**：`POST /auth/refresh`、`/auth/logout`、`/auth/password`、
`PATCH /admin/reports/{report_id}`、`POST /uploads/presign`。實際 **10 個**。

### B9 — 用 UTC 日期做新鮮度分桶
`date.today()` 讀**伺服器本地時區**，`created_at` 存 UTC → 同一請求在不同副本評分不同。
修 `datetime.now(timezone.utc).date()` 是一行，但**關鍵在把評分抽成純函數**
`score_post(post, signals, today) -> (float, list[str])`。原因：行內的 `date.today()`
讀的是測試控制不到的主機時區，唯一的測試法是在測不了時區的主機上打 HTTP。
把時鐘交給呼叫者之後，6 個純規則測試直接釘分層，第 7 個測試釘「呼叫者傳 UTC 日期」。
> **把時間當參數傳進去，是把時序邏輯變可測的最省力做法。**

### D4 — 抽資料擷取 hook
新建 `useRoomSocket`（來自 `chat/page.tsx`）、`useTravelHistories`（來自 `profile/page.tsx`）。
**核心規則：callback 與 resolver 一律經 ref 讀**，連線 effect 只依賴 `roomId`/`profileId`。
把 `t` 列進依賴（`exhaustive-deps` 會這樣建議）會在**每次切語言時重建 WebSocket**。
守衛（F2 的 per-socket 守衛與 `WeakSet`、F3 的 request counter 與兩個 busy guard）
**跟著邏輯搬進 hook**，否則下次改頁面又漏。
→ `check:ws-guard` 與 `check:profile-history` 兩支腳本**必須一併改指向新檔案**，
否則它們讀舊路徑會安靜地變成「0 個守衛 = 通過」。

### D5 — i18n 字典按功能拆 namespace

### D6 — 系統性併發測試

2. **每個測試同時斷言兩側**：liveness（≥1 成功，否則「拒絕所有人」也能滿足）
   與 safety（持久化狀態守住不變式）。只斷狀態碼會在「被拒的寫入已套用」時通過；
   只斷狀態會在「全部因無關理由被拒」時通過。

#### D6 負向驗證的兩個教訓（重要）
1. **第一次的 block 突變打在不可達的程式碼上。** 我改的是 `block_profile` 的
   **前置檢查**（`if existing:`），但真實競態走的是 `IntegrityError` 分支 ——
   被突變的那一行在競態下**根本不會執行**，所以「NOT-PINNED」什麼都沒證明。
   改打競態路徑（`return existing, False` → `True`）後才變紅。
2. **改對位置後才暴露測試的洞。** 測試只斷言 block **列數**，從不斷言**稽核列**，
   所以一個對既有列回報 `created=True` 的 `block_profile` 會照樣通過 ——
   而 `created` 正是 B5 的整個重點（呼叫端用 `created` 決定要不要寫 `USER_BLOCKED`）。
   補上稽核列計數後才 4/4 PINNED。

> **通則：「沒釘住」通常先代表測試有洞，不代表行為正確。**
> 而且要小心「突變的程式碼在該情境下不可達」這種假陰性 —— 它長得和「行為正確」一模一樣。
